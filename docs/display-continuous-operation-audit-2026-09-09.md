# Display continuous-operation audit — 9 September 2026

Follow-up: fixes and verification are recorded in [Display recovery changes](display-recovery-changes.md). The findings below describe the code before that remediation.

The most urgent remaining problems are at the integration boundaries: a refresh error still replaces usable content, a settings subscription can block startup, and malformed notice data can throw during rendering. This audit changes no application behavior. Earlier fixes remain in the working tree.

Scope: display layout and theme; prayer context, polling, daily rollover and overlays; rotator conditions, subscriptions and animations; slideshow scheduling, controls, synchronization and assets; weather client and server; donation settings; deployment checks; browser lifecycle and persistence; production dependency advisories.

Evidence: 12 targeted Jest/jsdom checks produced 11 failing assertions across 10 scenarios, plus one passing check documenting a persistent manual override. Both transition directions fail, accounting for the extra assertion. These are deliberately adversarial checks against proposed resilience expectations, not 11 independently observed production incidents. Requests, Firestore callbacks, timers and GSAP were mocked where needed. A stalled browser lock is a simulated environmental condition, not a demonstrated real-browser deadlock.

| A5 — Medium | A Rain notice restricted to Friday 18:00–19:00 is returned on Wednesday at 10:00. [Firebase listener error guidance](https://firebase.google.com/docs/firestore/query-data/listen#handle_listen_errors).

## Additional code and operational risks

These are inspection findings or deployment-dependent limitations, not additional failed automated checks.

| Area | What can happen during unattended operation | Follow-up |
| --- | --- | --- |
| Manual overrides and test controls | Pressing the downtime toggle twice leaves `downtimeOverrideActive` true after 24 simulated hours; there is no control to restore automatic mode. Ramadan preview also has no expiry. Prayer/post-prayer test signals remain positive in the provider, so their effects can replay on a later component remount. | Add an explicit Automatic mode and define preview expiry/one-shot consumption. Sources: `context/DebugContext.tsx:112`, `Components/PrayerOverlay.tsx:59`, `Components/PostPrayerTableOverlay.tsx:26`. |
| Reboot or reload during an outage | Timetable and slide-list recovery relies on memory. The app has no configured persistent Firestore cache or service worker for a dependable offline start. A tab reload or device reboot loses the app's in-memory fallback. | Store validated timetable data under its actual date and plan an offline application shell if offline boot is required. Browser HTTP caching alone is not a guarantee. Sources: `src/lib/firebase.ts`, `src/app/hooks/usePrayerTimesFromFirebase.ts:54`. |
| Tomorrow's timetable | The main display discards today's times at midnight correctly, but has no persistent prefetched next-day timetable. If connectivity fails across midnight, usable data for the new date may be unavailable despite an otherwise healthy device. The downtime component's separate tomorrow fetch does not populate the main hook. | Prefetch and validate upcoming dates into a shared date-keyed cache; never relabel yesterday's times. |
| Donation values during loading/failure | The donation panel starts every mount with £200,000 raised / £500,000 target. These are displayed as real totals before a snapshot arrives and remain if loading fails; invalid documents also normalize to those defaults. | Distinguish unknown values from configured totals and retain the last validated settings across slot remounts. Sources: `Components/Rotator/Specials/Donation.tsx:29`, `src/lib/firebase/donationSettings.ts:28`. |
| Device clock and time zone | Timetable date selection, prayer countdowns and slideshow windows use the device's local clock/zone. A UTC-configured UK kiosk in summer can display schedules an hour out. The application does not pin or verify `Europe/London`. This is not proof of a DST bug on correctly configured devices. | Define the mosque's time zone centrally, monitor clock configuration, and test both clock-change directions. Source: `src/lib/firebase/prayerTimes.ts:47` and display scheduling code. |
| Annual and post-prayer schedules | The special Eid al-Adha notice/greeting is hardcoded to May 2026 and does not roll forward annually. Separately, the five-minute post-prayer table window starts at jamaat, while the higher-layer prayer overlay occupies its first three minutes, leaving about two minutes of visibility. | Make event dates maintainable; agree whether five minutes is intended after the in-progress overlay. Sources: `src/lib/eidPrayerNotice.ts:1`, `src/lib/prayerTimeUtils.ts:126`, `Components/PrayerOverlay.tsx:28`, `Components/PostPrayerTableOverlay.tsx:9`. |
| Very distant event timers | The rotator schedules raw millisecond delays until the fixed Eid dates. Dates more than about 24.8 days away exceed the browser timeout limit. Current constants are already in the past, so this is dormant today and becomes relevant if dates are moved into the future. | Schedule bounded checkpoints and recalculate eligibility when they fire. Source: `Components/Rotator/index.tsx:121`. |
| Deployment interruption | A changed deployment version immediately reloads the display, including during a prayer or slideshow. It has no safe-window selection or offline-boot guarantee. | Defer routine updates to an appropriate display state, verify readiness, and provide a bounded update policy. Source: `Components/AutoReloadOnNewVersion.tsx:40`. |
| Animation and resource pressure | Message text tweens are created in a delayed callback outside the surrounding GSAP context; cleanup only clears that callback's timer. Already-started tweens are not explicitly killed there. Many/large images and long animated text can also stress kiosk memory/GPU. This audit did not establish an unbounded memory leak. | Own and kill those tweens explicitly; bound asset/text sizes and profile the real browser over repeated rotations. Source: `Components/Rotator/index.tsx:418`. |
| Growing content and request load | Every message snapshot fetches conditions separately for every message, with no collection size limit. Weather caching/coalescing is per server process rather than shared across all deployment instances. Application-level Firestore timeouts ignore late results but do not cancel the SDK's underlying `getDoc/getDocs` work. | Measure reads and pending work under sustained outages/content growth before redesigning; bound active content and use appropriate shared caching if deployment traffic warrants it. Sources: `Components/Rotator/Messages.tsx:59`, `src/app/api/weather/current/route.ts`, `src/lib/withTimeout.ts`. |
| Physical screen and recovery | No app-level wake-lock or kiosk watchdog is configured. OS sleep, power restoration, browser crash recovery, display retention/burn-in, and older browser CSS support remain device responsibilities. No display heartbeat or custom runtime-error reporting was found. | Verify managed kiosk/power settings and add health visibility. Test the actual screen resolution, browser version, sleep/resume, reboot and network recovery. |

Firestore web persistence must be configured explicitly for persistent caching; this project uses a plain `getFirestore(app)` instance. [Firebase offline persistence guidance](https://firebase.google.com/docs/firestore/manage-data/enable-offline).

Browser timeouts have a signed 32-bit delay limit and may run late when pages are inactive. Wall-clock recovery and actual browser suspension tests are therefore needed alongside fake-timer tests. [MDN timer behavior](https://developer.mozilla.org/en-US/docs/Web/API/Window/setTimeout#maximum_delay_value).

## Validation and retained reproductions

After archiving the diagnostics, the complete existing regression suite passed again: **264 tests across 37 suites**, using `npm test -- --runInBand --watch=false`. Console output from the existing Firebase tests includes intentionally mocked network, permissions and CSV errors; those tests passed. Passing this suite does not cover the newly reproduced integration gaps above.

The production dependency scan (`npm audit --omit=dev --json`) reported **zero known vulnerabilities** on the installed dependency tree. This is an advisory scan, not proof that every dependency or deployment is fault-free.

The targeted cases are archived under `docs/audits/2026-09-09/` as `.txt` files so the deliberately failing diagnostics do not alter the normal test suite. To reproduce, copy the three files back to `src/app/display/__tests__/`, removing only the final `.txt` suffix, then run:

```powershell
npm test -- --runInBand --watch=false --testPathPatterns='DisplayIntegration.audit|DisplayAssets.audit|DisplayWeather.audit'
```

The observed result is **11 failed / 1 passed**. The passing check documents the override persisting; it is not a resilience success. Remove only the restored audit copies afterwards, retaining the archived versions.

No live Firebase documents, settings, deployments or devices were changed. This audit did not perform a physical multi-day run, real-browser memory/GPU profiling, quota measurement, or verification of production hosting/power settings. A browser/device soak test should cover multiple midnights, both daylight-saving transitions, expired permissions, long outages followed by reconnection, two synchronized displays, malformed assets/content, and deployment/reboot recovery.
